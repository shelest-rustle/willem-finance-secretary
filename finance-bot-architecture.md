# Willem / Виллем — личный секретарь по ведению расходов

Telegram-бот + Google Sheets + Claude

## Персонификация

Имя: **Willem** (в коде, репозитории, конфигах) / **Виллем** (в текстах бота, обращении).

Роль: личный секретарь по ведению расходов — не "ассистент" и не "бот".

Тон сообщений:
- Краткость, без лишних вежливых оборотов и обращений типа "мадам"/"сэр"
- Обращение по имени пользователя, где уместно
- Формулировки-команды/констатации, а не вопросы-переспросы: "Записал", "Выберите категорию",
  "Оставьте комментарий", "Готово", "Не получилось записать, попробую позже"
- Никакой "ролевой болтовни" сверх необходимого — Виллем не "разговаривает", а фиксирует и подтверждает
- **Никакой оценочной/ограничительной лексики** ("превышено", "перерасход", "осторожно",
  "лимит нарушен" и подобное). Виллем не следит за тем, чтобы пользователь экономил —
  его роль строго фиксация и категоризация. При приближении/достижении лимита категории —
  нейтральная констатация цифр, без выводов и советов

Примеры реплик бота:
- При вводе суммы → "Выберите категорию"
- После категории → "Оставьте комментарий (или пропустите)"
- После записи → "Записал: 3 400 ₸ — Продукты"
- При приближении к лимиту (80%+) → "Записал: 3 400 ₸ — Продукты. По категории за месяц: 42 000 из 50 000 ₸"
- При достижении/превышении лимита → "Записал: 3 400 ₸ — Продукты. По категории за месяц: 51 200 из 50 000 ₸"
- При ошибке синка → сначала 1 автоматический ретрай записи в Sheets; если снова неудача →
  "Записал. Ошибка при отправке в Google Sheets, добавлено в очередь на отправку ночью"
- На `/today` → "Сегодня: 12 400 ₸ по 3 категориям"

## Цель проекта

Полная замена CoinKeeper собственным решением: Telegram-бот для быстрой фиксации трат,
sqlite как локальное хранилище-источник правды, синхронизация в Google Sheets,
Claude как аналитический слой поверх данных (через Google Sheets-коннектор).

## Стек

- Python 3.11+
- aiogram 3.x (Telegram bot framework)
- sqlite3 (стандартная библиотека, без ORM — объём данных не требует)
- gspread + google-auth (запись в Google Sheets через service account)
- APScheduler (ночная джоба досинхронизации)

## Архитектура потока данных

```
Пользователь → Telegram-бот (aiogram)
                   │
                   ▼
            sqlite (willem.db)   ← источник правды, пишется всегда первым
                   │
                   ▼
         попытка записи в Google Sheets (gspread)
                   │
          успех? ──┼── да → UPDATE transactions SET synced=1
                   │
                   └── нет → 1 автоматический ретрай
                              │
                       успех? ┼── да → synced=1
                              │
                              └── нет → synced=0, пользователю: "Ошибка при отправке
                                        в Google Sheets, добавлено в очередь на отправку ночью"
                              │
                              ▼
                 ночная джоба (APScheduler, напр. 03:00)
                 SELECT * WHERE synced=0 → повторная отправка

Google Sheets (Траты + Бюджет) → Google Drive-коннектор → Claude
```

## Функциональность бота (self-service)

1. **Расходы** — сумма → источник → категория → комментарий (опц.) → запись
2. **Доходы** — сумма → источник → комментарий (опц.) — пополняет баланс источника
3. **Переводы между источниками** — сумма → источник-откуда → источник-куда (например нал↔карта)
4. **Категории (CRUD)** — создание/редактирование/архивация; лимит + период
   (по умолчанию месяц, с возможностью задать неделю для конкретной категории)
5. **Источники (CRUD)** — создание/редактирование/архивация карт и нала
6. **Информирование о приближении к лимиту** — если расход доводит категорию до 80%+
   от лимита за период (включая случай превышения) — короткая констатация факта
   в том же сообщении, без блокировки записи и без оценочных формулировок
7. **Быстрые отчёты** — `/today`, `/week`, `/balances` (остатки по всем источникам)
8. **Правки последней записи** — `/last`, `/edit_last`, `/delete_last` (soft delete)

## Схема sqlite

Единый реестр операций (ledger) вместо отдельных таблиц для расходов/доходов —
так балансы по источникам и переводы считаются одним и тем же способом.

```sql
CREATE TABLE sources (
    id          TEXT PRIMARY KEY,   -- uuid4
    user_id     INTEGER NOT NULL,
    name        TEXT NOT NULL,      -- напр. "Kaspi Gold", "Halyk", "Наличные", "T-Bank RUB"
    type        TEXT NOT NULL,      -- card | cash
    currency    TEXT NOT NULL DEFAULT 'KZT',  -- валюта источника, фиксированная
    is_active   INTEGER NOT NULL DEFAULT 1
);

CREATE TABLE categories (
    id            TEXT PRIMARY KEY, -- uuid4
    user_id       INTEGER NOT NULL,
    name          TEXT NOT NULL,
    limit_amount  REAL,             -- NULL = без лимита
    limit_period  TEXT DEFAULT 'month',  -- month | week
    is_active     INTEGER NOT NULL DEFAULT 1
);

CREATE TABLE transactions (
    id                TEXT PRIMARY KEY,     -- uuid4, ключ дедупа в Sheets
    user_id           INTEGER NOT NULL,
    type              TEXT NOT NULL,        -- expense | income | transfer
    amount            REAL NOT NULL,        -- списание: сумма в валюте source_id
    currency          TEXT NOT NULL,        -- = валюта source_id, дублируется для читаемости в Sheets
    target_amount     REAL,                 -- только transfer: сумма зачисления в валюте target_source_id
    target_currency   TEXT,                 -- только transfer: = валюта target_source_id
    source_id         TEXT NOT NULL REFERENCES sources(id),
    target_source_id  TEXT REFERENCES sources(id),  -- только для transfer
    category_id       TEXT REFERENCES categories(id),  -- только для expense
    comment           TEXT,
    created_at_utc    TEXT NOT NULL,        -- ISO 8601, UTC. Конвертация в Almaty tz — на отображении
    synced            INTEGER NOT NULL DEFAULT 0,
    deleted           INTEGER NOT NULL DEFAULT 0
);

CREATE INDEX idx_synced ON transactions(synced);
CREATE INDEX idx_type ON transactions(type);
```

Курс перевода нигде не хранится и не считается автоматически — при кросс-валютном переводе
пользователь вводит фактически списанную сумму (`amount`/`currency`) и фактически зачисленную
(`target_amount`/`target_currency`); неявный курс = `amount / target_amount`, восстанавливается
постфактум при необходимости, а не диктуется ботом (курс/способ обмена гуляет — наличка, крипта и т.д.).

Баланс источника считается в его собственной валюте: сумма income + входящие transfer
(по `target_amount`, если валюта совпадает с валютой источника) − expense − исходящие transfer
(по `amount`). Кросс-валютные суммы не складываются друг с другом — каждый источник видит
только операции в своей валюте.

## Категории (пример, зафиксировать финальный список до старта разработки)

Продукты, Кафе/рестораны, Транспорт, Жильё/коммуналка, Здоровье, Спорт,
Одежда, Развлечения, Подарки, Питомец (Тёма), Прочее

Лимит задаётся при создании категории: сумма + период (месяц по умолчанию, неделя — опционально).
Лимит необязателен (NULL = без ограничения).

> Важно: названия категорий должны 1:1 совпадать с категориями в таблице бюджета,
> иначе Claude не сможет корректно сопоставлять план/факт.

## Источники (пример, зафиксировать финальный список до старта разработки)

Kaspi Gold, Halyk, [третья карта], Наличные — тип card/cash для каждой.

## Сценарии бота (happy path)

**Расход:**
1. `/add` или число в сообщении → кнопки источников → кнопки категорий
2. Комментарий (или кнопка "Пропустить")
3. Запись в sqlite → проверка лимита категории за период → если приближается/превышен —
   предупреждение в том же сообщении → попытка синка в Sheets → "Записал: ..."

**Доход:**
1. `/income` → сумма → источник → комментарий (опц.) → запись, баланс источника растёт

**Перевод:**
1. `/transfer` → сумма (списание) → источник-откуда → источник-куда
2. Если валюты источников совпадают → зачисление = списанию автоматически
3. Если валюты разные → бот дополнительно спрашивает "Сколько зачислилось на [источник-куда]?"
   (фактическая сумма, без расчёта курса) → запись, балансы обоих источников обновляются
   каждый в своей валюте

**Управление категориями/источниками:**
- `/categories` → список с кнопками (добавить / редактировать / архивировать)
- `/sources` → аналогично

**Отчёты и правки:**
- `/today`, `/week` — сумма по категориям за период
- `/balances` — остаток по каждому источнику
- `/last` — последние 5 операций
- `/edit_last`, `/delete_last` — правка/soft delete последней операции

## Google Sheets

- Один лист "Транзакции" — append-only, колонки соответствуют полям transactions
  (включая type: expense/income/transfer, названия источника и категории вместо id — для читаемости)
- id используется как ключ дедупа: перед вставкой в джобе проверять, нет ли уже такого id в листе
- Отдельный существующий лист/файл "Бюджет" — не трогаем ботом, только читаем через Claude

## Безопасность

- Бот отвечает только на сообщения от заданного `user_id` (свой telegram id, хардкод в конфиге/.env)
- Service account credentials для gspread — только в .env / secrets, не в репозитории
- .gitignore: `.env`, `*.db`, `credentials.json`

## Хостинг

Нужен always-on процесс (не GitHub Actions — тот только по расписанию, не для приёма апдейтов).
Варианты: VPS, Fly.io/Railway free tier, локально дома (raspberry pi / фоновый процесс).

## Порядок разработки (предложение для первой сессии)

1. Инициализация проекта, структура папок, .env, requirements
2. Модуль sqlite: схема (sources, categories, transactions), функции insert/select/update
3. Сидинг стартовых источников и категорий (можно через `/sources add`, `/categories add`
   либо seed-скриптом при первом запуске)
4. aiogram: FSM для флоу расхода — сумма → источник → категория → комментарий
5. Проверка лимита категории перед подтверждением записи (SELECT сумма расходов
   по category_id за текущий период vs limit_amount)
6. FSM для доходов и переводов — переиспользуют часть логики флоу расхода
7. Интеграция gspread: запись строки + проверка дублей по id
8. Джоба APScheduler для досинка synced=0
9. Команды: `/today`, `/week`, `/balances`, `/last`, `/edit_last`, `/delete_last`
10. Тестовый прогон полного цикла: расход / доход / перевод → sqlite → sheets → отчёты
