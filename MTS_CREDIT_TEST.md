## 2. Таблица 1 «ПЛАТЕЖИ ПО ГРАФИКУ» (строки 6–31) — только обычные ежемесячные платежи

Заголовки (row 6) — **колонка «Тип операции» убрана целиком**, колонки сдвинуты и переименованы:

`№ | Дата платежа | План платёж | Факт оплаты | Проценты за период | Погашено долга (обычным платежом) | Досрочно погашено в этом периоде (авто) | Остаток долга | Что сделать, если заплатила больше плана | Остаток по графику банка (для сверки) | Оплачено накопительно (обычные платежи) | Комментарий`

Строка 7 — стартовая точка на дату среза (как в v1: `B7=$J$4`, `H7=$N$4`, `K7=$K$4`, плюс новая `L7` — текстовая пометка «Старт — остаток тела долга на дату среза»).

Типовая строка (пример row 9):

```
A9 = "2"                                   — литерал, порядковый номер (как и раньше)
B9 = =EDATE(B8;1)                          — дата = дата предыдущей строки + 1 месяц
C9 = =IF(N9;
        -PMT($E$4;DATEDIF(B8;$H$4;"m");H8);   — если когда-либо включали "уменьшить платёж" — аннуитет от текущего остатка
      IFERROR(INDEX($C$94:$C$152;O9);          — иначе плановый платёж из графика банка по номеру O9
              IF(B9>=$G$4;$I$4;$F$4)))          — а если график банка кончился — "Платёж №2"/"Платёж №1" по дате
D9 = (пусто, ждёт факта)                    — сюда вписывается реально заплаченная сумма (Факт оплаты)
E9 = =IF(D9="";"";H8*$E$4)                  — проценты за период = остаток на начало периода * месячная ставка
F9 = =IF(D9="";"";D9-E9)                    — погашено долга обычным платежом = факт - проценты
G9 = =SUMIFS($B$35:$B$64;$A$35:$A$64;">"&B8;$A$35:$A$64;"<="&B9)
                                             — ⭐ НОВОЕ: сумма всех досрочных взносов из Таблицы 2,
                                               сделанных строго между датой предыдущего и текущего обычного платежа
H9 = =IF(D9="";H8-G9;H8-F9-G9)              — остаток долга = предыдущий остаток минус (обычное погашение, если было) минус досрочные взносы за период
I9 = "Сократить срок"                       — литерал с data validation (список: "Сократить срок" / "Уменьшить платёж")
J9 = =IFERROR(INDEX($F$94:$F$152;O9);" — ") — остаток по графику банка, справочно
K9 = =IF(D9="";K8;K8+D9)                    — накопительно оплачено ПО ГРАФИКУ (без досрочных — те считаются отдельно)
N9 = =OR(N8; I8="Уменьшить платёж";
           COUNTIFS($A$35:$A$64;">"&B8;$A$35:$A$64;"<="&B9;
                     $C$35:$C$64;"Уменьшить платёж")>0)
                                             — ⭐ флаг "уменьшение платежа когда-либо включалось" теперь смотрит
                                               и на I-колонку Таблицы 1, И на С-колонку Таблицы 2 (досрочные взносы)
O9 = =O8+1                                  — указатель на график банка (теперь растёт всегда — "Досрочный взнос"
                                               как отдельного типа строки больше не существует, поэтому он не может
                                               пропускать шаг, как было в v1)
```

**Важно:** `D8` (самая первая, «текущая к оплате» строка) — до сих пор формула `=C8` (то есть по умолчанию «зеркалит» план), а не пустая, и не литерал! Это одинаково для всех трёх кредитных листов на строке 8. Начиная с `D9` и далее — уже честно пустые ячейки (ни формулы, ни значения) до тех пор, пока туда не впишут факт.

Из этого следует **правило поиска «текущей» строки для обычного платежа**: нельзя просто искать первую строку с пустым `D`. Нужно смотреть **формулу** ячейки (`valueRenderOption=FORMULA`), а не отформатированное значение:
- `D<row>` — пусто → ещё не платили, это кандидат;
- `D<row>` — формула (начинается с `=`) → тоже ещё не платили по-настоящему, это дефолтный «зеркальный» плейсхолдер, тоже кандидат;
- `D<row>` — голое число без `=` → уже вписан реальный факт оплаты, пропускаем.

Первая строка, не подпадающая под «уже оплачено», и есть строка для записи текущего платежа.

## 3. Таблица 2 «ДОСРОЧНЫЕ ПЛАТЕЖИ И ПЕРЕПЛАТЫ» (строки 33–65) — НОВОЕ

```
A33: "ДОСРОЧНЫЕ ПЛАТЕЖИ И ПЕРЕПЛАТЫ"          — заголовок блока
Row 34 (шапка): "Дата взноса" | "Сумма" | "Что сделать с переплатой" | "Комментарий"
Rows 35–64 (30 строк, зарезервировано под записи):
    A = дата взноса (литерал, вручную)
    B = сумма (литерал, вручную)
    C = "Сократить срок" / "Уменьшить платёж" — data validation ONE_OF_LIST на ВСЕХ 30 строках (35–64),
        но литерал-дефолт "Сократить срок" выставлен пока только в первой строке (A35 и B35 — пустые, C35 = "Сократить срок")
    D = комментарий (литерал, вручную, опционально)
Row 65: "Итого" | B65 = =SUM(B35:B64)
```

Это **плоская append-таблица без построчных формул** (кроме итоговой суммы) — принципиально другая механика по сравнению со старой Таблицей 1: здесь ничего не завязано «от строки выше», поэтому новую запись можно просто дописать в первую пустую строку диапазона `35:64`, без копирования формул и без `InsertDimensionRequest`. Ровно то, что и предлагалось как альтернатива вставке строк.

Эффект взноса **автоматически подхватывается** Таблицей 1 через `SUMIFS` в колонке `G` (см. выше) — как только дата взноса попадает в промежуток между двумя соседними обычными платежами, её сумма учитывается в остатке долга следующей же обычной строки. Никакого ручного переноса не требуется.

**Ёмкость:** 30 строк на весь срок кредита. Для этого кредита (59 обычных платежей за ~5 лет) это с большим запасом — вряд ли когда-либо станет проблемой, в отличие от Таблицы 1 (та по-прежнему конечна и требует ручного «протягивания» вниз). Важно: конкретная граница Таблицы 1 — **разная у разных кредитов** (см. раздел 8, четвёртый кредит «Tinkoff REF Кредит Лики» заполнен сразу на весь срок, до строки 43, а не 31) — реализация вычисляет её на лету по самому листу, а не хардкодит.

## 5. Блок «ПРАВИЛА» (строки 74–90) — переписан под новую структуру

Коротко:
- **Таблица 1** — для обычных ежемесячных платежей: вписать факт оплаты в «Факт оплаты» очередной незаполненной строки сверху вниз, больше ничего трогать не нужно. Досрочные взносы сюда **не** вписывать.

- Про «Остаток по графику банка» — то же самое: справочно, расходится с реальным остатком после первого досрочного платежа.

## 8. Итог: подходит ли новая структура под согласованный флоу?

**Да, подходит, и даже лучше, чем предполагалось.** Новая структура снимает главную сложность
предыдущего плана — необходимость вставки строки и копирования формул для «Досрочного взноса»
(это был явно обозначен как «этап 2, сложнее» в прошлом обсуждении). Теперь оба сценария —
одинаково простые точечные операции:

| Сценарий | Что делает бот (было) | Что делает бот (сейчас) |
|---|---|---|
| Обычный платёж | найти строку с пустым `E`, записать туда сумму | найти строку в `8:31`, где `D` пусто **или** это формула (не литерал) — записать туда сумму в `D`, при выборе «уменьшить платёж» — переписать `I` |
| Досрочный взнос / переплата | вставить строку в середину графика, скопировать формулы соседней строки (`InsertDimensionRequest` + `copyPaste`) — хрупко | найти первую пустую строку в `35:64`, записать `A` (дата), `B` (сумма), `C` (выбор), `D` (комментарий) — обычный `update`, без структурных изменений листа |

Оба случая теперь имеют **симметричную сложность** — «найти нужную строку по простому критерию и переписать несколько ячеек». Это значит, что предыдущее деление на «этап 1 сейчас / этап 2 позже» больше не обязательно по техническим причинам — можно реализовывать оба сценария сразу одним и тем же родом кода (только с разными диапазонами поиска и разным набором колонок для записи).

Что по-прежнему нужно учесть в реализации:
1. **Поиск целевой строки для обычного платежа** — по признаку «`D` пусто ИЛИ является формулой», не по «пусто» (см. раздел 2). Нужно читать `valueRenderOption=FORMULA`, а не только отформатированное значение.
2. **Поиск первой свободной строки для досрочного взноса** — по колонке `A` (дата) в диапазоне `35:64`: первая пустая.
3. **Ёмкость обеих таблиц конечна** — 24 (точнее, «сколько успели заполнить формулами», сейчас 31-я строка последняя) для обычных платежей и 30 для досрочных. Стоит на всякий случай проверять остаток свободных строк и предупреждать, если он близок к нулю (для Таблицы 2 это скорее теоретический случай — 30 досрочных взносов за весь кредит маловероятны).
4. Подкатегорию-маппинг «какой это кредит» (МТС Лика / Tinkoff Лика / МТС Ярослав → соответствующий лист) — согласовано раньше, не поменялось.
5. Общий механизм точечной записи в конкретный лист/диапазон (не `append_row`) в кодовой базе всё ещё придётся построить с нуля — но теперь это будет **одна и та же простая функция** для обоих сценариев (обычный/досрочный), просто с разными целевыми диапазонами и колонками, а не две принципиально разные операции.

## 9. Статус реализации (актуально на сейчас)

Флоу и запись в кредитные листы реализованы (`willem/credit_sheets.py`, флоу в
`willem/bot/handlers/expense.py`). Отличия от плана в разделе 8, по опыту реальных
данных:

- **Границы обеих таблиц не хардкодятся, а определяются на лету** по самому листу
  (`_table_layout` ищет заголовок «ДОСРОЧНЫЕ ПЛАТЕЖИ И ПЕРЕПЛАТЫ» и строку «Итого» после
  него) — выяснилось, что у разных кредитов Таблица 1 разной длины (`8:31` у трёх
  первых, `8:43` у «Tinkoff REF Кредит Лики», где весь график на 36 платежей заполнен
  сразу). Жёсткая константа `31` не подошла бы для четвёртого кредита.
- **«Что сделать с переплатой» бот спрашивает только для досрочного взноса.** Для
  обычного платежа по графику этот вопрос убран из флоу целиком — в Таблице 1
  остаётся дефолтное «Сократить срок», уже проставленное в самом листе, бот его не
  трогает (по правке Лики: эта развилка имеет смысл только для случая 2 из правил).
- **Кредитов сейчас четыре**, не три: «МТС Кредит Лики», «Tinkoff Кредит Лики»,
  «МТС Кредит Ярослава», «Tinkoff REF Кредит Лики» (новый, реальный — лист и условия
  уже заполнены, кредит ещё не начат на дату среза). Подкатегории/источник/маппинг —
  `profiles/pantalone.yaml` (`seed_categories`, `seed_sources`, `credit_sheets`);
  на уже засеянном проде применяются через `scripts/migrate_credit_categories.py` и
  `scripts/migrate_credit_source.py` (dry-run по умолчанию, `--write` — реально).
